# 截图识别架构（OCR）

## 1. 目标与范围

从一张棋盘图片（截图/拍照）识别出局面，生成 FEN 并载入局面编辑器，供用户校正后继续。

对照网页版基线：网页版「棋盘图片识别」明确说明「建议清晰无干扰且垂直棋盘，识别率不是很高，识别有误可手动摆棋」。本项目把**手动校正**作为一等公民，而非追求完美识别。

## 2. 管线

```
图片输入 → 预处理 → 棋盘检测 → 网格切分 → 棋子分类 → FEN 合成 → 人工校正
```

| 步骤 | 职责 | 备注 |
|------|------|------|
| 预处理 | 灰度/去噪/透视校正 | 提升后续鲁棒性 |
| 棋盘检测 | 定位 10×9 网格角点 | 支持透视变形校正 |
| 网格切分 | 得到 90 个格子的子图 | |
| 棋子分类 | 识别每格：空/红黑 7 种棋子 | 核心难点：汉字 + 红黑区分 |
| FEN 合成 | 分类结果 → 局面 | 缺失/不确定格置空并标记 |
| 人工校正 | 在局面编辑器中修正 | 必选，保证最终正确性 |

## 3. 技术选型（待确认）

- 本地优先：倾向在 Rust 侧或本地模型做分类，避免上传图片。
- 候选方案（`NEEDS_VERIFICATION`，均需验证识别率与许可）：
  1. 传统 CV（角点检测 + 模板匹配/简单分类器）——无需大模型，但泛化弱。
  2. 轻量本地模型（如 ONNX 小分类网络）——识别率更好，需选型与权重许可确认。
  3. 云端 OCR/识别 API——识别率最高，但违背本地优先，仅作可选增强。
- 首版策略：先以「传统 CV + 人工校正」落地可用的最低实现；识别率不足再迭代模型方案。

## 4. 接口

```rust
pub struct OcrInput { pub image: Vec<u8> }          // PNG/JPEG 字节
pub struct OcrCell { pub rank: u8, pub file: u8, pub piece: Option<Piece>, pub confidence: f32 }
pub struct OcrOutput { pub cells: Vec<OcrCell>, pub fen_hint: String }

pub trait OcrEngine {
    fn recognize(&self, input: &OcrInput) -> OcrResult<OcrOutput>;
}
```

- 输出始终带 `confidence` 与 `fen_hint`，低置信度格子在 UI 中高亮，引导用户校正。
- OCR 在后台线程执行（阻塞任务），完成后通过 event 返回，避免卡 UI。

## 5. 依赖与许可

- 图片解码：Tauri/Rust 侧标准图像库（如 `image` crate）。
- 若引入本地模型，权重与运行时许可须纳入 `docs/licensing.md` 风险清单。
- 不将用户图片上传到第三方，除非用户显式选择云端方案。

## 6. 测试

- 合成图片测试集（程序生成标准棋盘截图）验证几何检测与分类的正确率阈值。
- 真实截图回归集（若干张已知局面）作为黄金基线，识别失败仅降级为「提示手动摆棋」，不阻塞功能。
- OCR 属于可降级功能，测试以「不崩溃 + 输出合法结构 + 可人工校正」为最低验收线。
